────────────────────────────────────────────────
main.py
────────────────────────────────────────────────
FastAPI 애플리케이션의 진입점이며 모든 라우터를 한곳에 등록한다.

로직
  · lifespan(앱 수명주기)에서
      - 시작 시 : DB 커넥션 풀 init() → 스케줄러 start()
      - 종료 시 : 스케줄러 stop() → DB 풀 dispose()
    즉 "DB가 살아있는 동안만 서버가 요청을 받도록" 보장한다.
  · CORSMiddleware로 허용 오리진을 명시한다.
      - Render 배포 도메인, capacitor://localhost(모바일 앱),
        localhost(개발) 만 허용하여 외부 무단 호출을 차단한다.
  · include_router(..., prefix="/api") 로 전 라우터에 /api 접두사를 붙인다.
    → 프론트는 항상 "/api/..." 로 호출한다.

조건식 이유
  · allow_origins를 *(전체)로 두지 않은 것은 credentials(쿠키/인증)를
    허용하면서 보안을 유지하기 위함이다.


────────────────────────────────────────────────
scheduler.py  /  router/HeartScheduler.py
────────────────────────────────────────────────
역할
  10초마다 raw 심박수(heart_rate_logs)를 user_id별 평균으로 집계해
  watch_heart_logs에 저장하는 백그라운드 작업.

로직
  1. cutoff = 현재시각 - 10초.  created_at <= cutoff 인 raw 데이터만 집계
     → "10초가 지나 더 들어올 일이 없는 데이터"만 안전하게 처리.
  2. user_id별 AVG(bpm) 계산 후 watch_heart_logs에 INSERT.
  3. 집계에 사용한 raw 행은 DELETE(중복 집계 방지 + 용량 절약).
  4. watch_heart_logs는 user_id별 최신 120개만 유지(OFFSET 120 이후 삭제).
     → 약 20분치 데이터만 보관.

조건식 이유
  · ON CONFLICT DO NOTHING : 같은 버킷이 중복 삽입되는 것을 막는다.
  · pool is None 체크 : 서버 부팅 직후 DB 풀이 준비되기 전에
    스케줄러가 먼저 돌면 None 접근 오류가 나므로 방어.

(주의) scheduler.py와 HeartScheduler.py가 유사 기능을 한다.
       실제 가동되는 것은 main.py가 import하는 scheduler.py 쪽이다.

────────────────────────────────────────────────
router/UserLoginRouter.py
────────────────────────────────────────────────
역할
  로그인. 사용자가 입력한 아이디/비밀번호를 DB 정보와 비교한다.

로직
  1. user_login_id로 app_user 행 조회.
  2. 행이 없으면 401(아이디/비번 틀림) — 아이디 존재 여부를 노출하지 않으려
     "아이디 또는 비밀번호가 틀렸습니다"로 통일.
  3. is_active=false 이면 403(비활성 계정).
  4. 입력 비밀번호를 SHA-256으로 1차 해싱 → 저장된 Argon2 해시와 verify.
     (가입 때와 동일한 2단계 방식이라 검증이 일치한다.)
  5. password_hash == "PENDING" 이면 401(가입 미완료 계정).

조건식 이유
  · "다른 경우(불일치) 조건식"이 여러 개인 이유:
      - 행 없음 / 비활성 / 가입미완료 / 비번불일치를 각각 다른 상태코드로
        구분해 프론트가 적절한 안내를 띄우도록 하기 위함.
  · 비번 불일치와 아이디 없음을 같은 메시지로 처리하는 것은
    계정 존재 여부를 공격자에게 흘리지 않기 위한 보안 처리.


────────────────────────────────────────────────
router/MembershipRouter.py
────────────────────────────────────────────────
역할
  회원가입 2/3(기본정보 register)과 3/3(추가정보 extra) 처리.

로직 (register)
  1. email_token이 이메일과 일치하는지 확인(인증을 거친 사람만 가입 가능).
  2. 비밀번호 SHA-256 → Argon2 2단계 해싱.
  3. 트랜잭션 내에서:
     - 이메일 인증 단계에서 만들어둔 PENDING 계정을 찾는다.
     - 이미 is_active이거나 hash!='PENDING' 이면 409(이미 가입됨).
     - email_verified_at 없으면 403(이메일 미인증).
     - 전화번호 중복 검사(다른 user가 쓰면 409).
     - PENDING → ACTIVE로 UPDATE + user_profile UPSERT.

로직 (save_extra)
  · 설문형 한글 라벨(주 2~3회 등)을 숫자/분 단위로 변환(map_* 헬퍼).
  · 스키마에 없는 항목(흡연 시작나이, 담배 종류)은 note JSON으로 묶어 저장.
  · health_behavior_snapshot에 UPSERT(ON CONFLICT user_id DO UPDATE).

조건식 이유
  · UniqueViolationError를 잡아 "어느 컬럼이 중복인지"에 따라
    전화/로그인ID/이메일별로 다른 409 메시지를 돌려준다(사용자 안내 명확화).

router/EmailRouter.py
────────────────────────────────────────────────
역할
  회원가입용 이메일 인증번호 발송/검증.

로직 (send-verification)
  1. 이메일 형식 검사(@ 포함).
  2. 6자리 코드 생성 → SHA-256 해싱하여 저장(원문 미저장).
  3. 기존 PENDING 계정이 있으면 재사용, 없으면 PENDING 계정 신규 생성.
  4. 이전 진행 중 코드 무효화(used_at 세팅) 후 새 토큰 INSERT(만료 10분).
  5. 즉시 메일 발송(성공/실패를 바로 응답에 반영).

로직 (verify)
  · 코드 해시 + 미사용 + 미만료 조건을 모두 만족하는 토큰만 통과.
  · 통과 시 used_at 기록 + app_user.email_verified_at 갱신.

조건식 이유
  · "이미 가입된 이메일"은 400으로 막아 중복가입 방지.
  · 토큰을 해시로 저장하는 것은 DB 유출 시에도 코드가 노출되지 않게 함.

router/MotionData.py   ★핵심 (Watch 모션 → 흡연 감지)
────────────────────────────────────────────────
역할
  Watch가 보낸 30초 윈도우(24피처)를 저장하고, 흡연 여부를
  2단계(Layer1 모델 + Layer2 HLSDA 보정)로 예측해 결과를 돌려준다.

데이터 흐름
  Watch(50Hz, 30초) → 24피처 → iPhone → POST /api/motion/window → 이 파일

로직 (POST /window)
  1. 유저 존재 확인(없으면 404).
  2. watch_motion_features 테이블에 24피처 INSERT(RETURNING으로 저장행 회수).
  3. 방금 저장한 measured_at 기준 "최근 5분(300초)" 윈도우만 조회.
     - session_start = measured_at - timedelta(300) 를 파이썬에서 계산해 파라미터로 전달.
     - 이렇게 해서 "현재 세션에서 수집된 윈도우들"만 모델 입력으로 사용한다
       (과거 DB 이력 전체를 쓰지 않음).
  4. 세션 윈도우들의 피처를 컬럼별 평균 → 평균 피처 1세트 생성.
  5. Layer1 : smoking_predictor.predict_smoking(평균피처) → raw 라벨/확률.
  6. Layer2 : 사용자별 in-memory 예측 시퀀스에 raw를 추가하고
              hlsda_correct()로 보정 → 최종 라벨 결정.
  7. is_smoking(보정값)/confidence/raw_label/corrected_label/세션윈도우수를
     응답에 실어 반환(이 AI 결과는 DB에 저장하지 않음, 응답 전용).

세션 캐시(_pred_cache / _pred_times)
  · 사용자별 raw 예측 라벨 리스트를 메모리에 보관(HLSDA가 시퀀스를 봐야 하므로).
  · TTL 400초(5분 세션 + 여유 100초) 초과 시 자동 리셋.
  · DELETE /{user_id}/session : 수집 종료 시 캐시 강제 초기화.

조건식/설계 이유
  · _naive() 로 timezone 제거 :
      measured_at 컬럼이 'timestamp without time zone'(naive)인데
      timezone-aware 값을 넣으면 asyncpg가 빼기 연산에서 오류를 낸다.
      그래서 UTC로 변환 후 tzinfo를 제거한 naive datetime으로 저장한다.
  · INTERVAL SQL 대신 timedelta 파라미터 사용 :
      naive 컬럼에 "$2 - INTERVAL" 연산을 쓰면 타입 충돌이 나서,
      세션 시작 시각을 파이썬에서 미리 계산해 넘긴다.
  · 세션 평균을 쓰는 이유 :
      한 윈도우만 보면 노이즈에 흔들리므로 5분 세션 평균으로 안정화.

reanalyze (GET /{user_id}/reanalyze)
  · 수동 수집 후 "모델에 입력" 버튼용. 새 INSERT 없이 최근 5분 데이터로
    다시 평균→Layer1→HLSDA 예측만 수행해 결과 반환.

router/smokingAiModel/smoking_predictor.py   (Layer1)
────────────────────────────────────────────────
역할
  smoking_rf_binary.pkl(sklearn Pipeline: StandardScaler+RandomForest)로
  흡연 여부를 예측하는 1차 분류기.

로직
  · pkl 구조 : {pipeline, features(24개), classes(['non_smoke','smoke'])}.
  · DB 피처명 → pkl 피처명 매핑(_DB_TO_PKL):
       accel_x_max → acc_x_max,  accel_x_skewness → acc_x_skew,
       accel_x_kurtosis → acc_x_kurt ...
  · 입력 벡터는 반드시 pkl의 features 순서대로 구성한다
       row = [pkl_vals.get(f, 0.0) for f in _features]
    → 입력 dict 순서와 무관하게 항상 학습 때와 같은 순서를 보장.
  · predict로 라벨, predict_proba로 smoke 확률(confidence) 산출.

조건식 이유

    (피처 하나가 빠져도 예측 자체는 진행되게 하기 위함).
  · classes_.index("smoke") 로 smoke 위치를 찾는 것은 클래스 순서가
    바뀌어도 올바른 확률을 읽기 위함.

App/PhoneConnectivityManager.swift   ★iPhone↔Watch 통신 허브
────────────────────────────────────────────────
역할
  WatchConnectivity로 Watch와 양방향 통신하고, Watch가 보낸 데이터를
  백엔드 API로 중계하며, AI 결과를 다시 Watch로 돌려보낸다.

iPhone → Watch
  · sendUserInfoToWatch : updateApplicationContext로 로그인정보 전송(영속 컨텍스트).
  · sendQuitDaysToWatch : 금연일수 전송.
  · sendCrisisAlertToWatch : 위기 알림(즉시 sendMessage).

Watch → iPhone (수신 분기)
  · didReceiveMessage(즉시) / didReceiveUserInfo(큐) 두 경로 모두 처리.
  · type별 분기:
      - requestUserInfo : 저장된 유저정보 재전송.
      - motionWindow    : 24피처 → /api/motion/window 로 POST → AI결과 처리.
      - heartRateBatch  : /api/UserHeart/batch 로 POST + 최신BPM 캐시/이벤트.
      - hrvSpike        : iPhone 로컬 알림 표시.
      - sessionEnd      : DELETE /api/motion/{id}/session (HLSDA 캐시 리셋).
      - reanalyzeRequest: GET /api/motion/{id}/reanalyze (재예측).

handleMotionWindow 로직
  · 6축×4통계(max/min/skewness/kurtosis) 24개 키를 파싱.
  · 누락 키는 0.0으로 채우고 경고 로그(피처 부족해도 전송은 진행).
  · 응답을 handleSmokingPrediction으로 넘긴다.

handleSmokingPrediction 로직
  · is_smoking이 있으면(서버 정상) 흡연/비흡연 상관없이
    "motionResult" 메시지를 항상 Watch로 전송한다.
      - 이유 : 예전에는 흡연일 때만 보내서 비흡연이면 Watch에 결과가
        안 떴다. 결과 카드를 항상 갱신하려고 항상 전송으로 바꿈.
  · reachable이면 sendMessage, 실패/미연결이면 transferUserInfo로 재시도.

조건식 이유
  · 두 수신 경로(message/userInfo)를 모두 다루는 것은 Watch가 연결 상태에 따라
    즉시(sendMessage) 또는 큐(transferUserInfo)로 보내기 때문.

GeumyeonWatch Watch App/Managers/MotionManager.swift   ★센서 수집
────────────────────────────────────────────────
역할
  손목 모션을 50Hz로 수집해 30초마다 24개 통계 피처로 요약하고 전송한다.
  수집 중에는 화면을 계속 켜둔다.

로직
  · startRecording(mode) : .manual(버튼) / .auto(HRV 자동) 모드로 시작.
      - CMMotionManager 50Hz로 6축(가속도 3 + 자이로 3) 누적.
      - 30초 windowTimer마다 flushWindow, 1초 sessionTimer로 남은시간 카운트.
      - WKExtendedRuntimeSession으로 수집 중 화면 유지.
  · computeStats : 각 축의 max/min/왜도(skewness)/첨도(kurtosis) 계산.
      - 표준편차가 0에 가까우면(거의 정지) 왜도·첨도를 0으로(0나눗셈 방지).
  · flushWindow : 24피처 payload(키명=DB 컬럼명) 구성 → transferUserInfo 전송.
      - isReachable로 "직접 전송 / 큐 저장"을 로그·알림으로 안내.
  · stopRecording : 타이머·센서·화면세션 정리, 남은 버퍼 flush.
      - 수동 모드면 pendingManualInput=true(=> "모델에 입력" 버튼 노출) + 완료 알림.

핵심 수정/조건식 이유
  · 수집 중간 자동 중단 방지 :
      WKExtendedRuntimeSession이 만료/오류로 무효화되면 화면이 꺼지고
      앱이 백그라운드로 가 타이머가 멈춘다. 그래서 didInvalidateWith에서
      isRecording이면 세션을 즉시 재시작한다.
      (willExpire에서 새로 만들면 이전 세션과 겹쳐 .sessionInProgress
       오류가 나므로, 재시작은 무효화 콜백에서만 한다.)
  · payload 키를 DB 컬럼명과 동일(accel_x_skewness 등)하게 맞춰
    iPhone→백엔드까지 변환 없이 그대로 흐르게 한다.

GeumyeonWatch Watch App/Managers/HealthManager.swift   ★심박/HRV
────────────────────────────────────────────────
역할
  HealthKit으로 실시간 심박수를 읽고, 10초마다 HRV(RMSSD)를 계산해
  급상승(흡연 의심) 시 자동 수집 트리거를 발생시킨다.

로직
  · requestAuthorization : 심박 읽기 권한 요청 후 HR 쿼리 + HRV 모니터링 시작.
  · startHeartRateQuery : HKAnchoredObjectQuery로 새 심박 샘플을 실시간 수신.
      - 최신 BPM을 currentBPM에 반영, bpmHistory(최대 20개)에 누적.
      - 세션 중이면 hrBuffer에도 쌓아 30초마다 배치 전송.
  · computeRMSSD : BPM → RR간격(ms=60000/BPM) 변환 후
      연속 차이 제곱 평균의 제곱근(=RMSSD).
  · evaluateHRV(10초마다):
      - 기저값(baselineRMSSD)을 EMA(0.8*기존+0.2*현재)로 갱신.
      - rmssd > baseline*1.8 이면 급상승으로 판정 → handleHRVSpike.

조건식 이유
  · baseline < 최소값(10ms)일 때 초기화 : 측정 초반 불안정 구간 보호.
  · SPIKE_COOLDOWN(300초) : 한 번 트리거 후 5분간 재트리거 방지(과민반응 차단).
  · bpmHistory>=3 일 때만 계산 : 표본이 너무 적으면 RMSSD가 무의미하므로.
